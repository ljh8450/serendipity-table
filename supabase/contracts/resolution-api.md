# Match resolution API

2026-10-16 · STA-05/06 · PAY-03 · PRD15 · RES-001/OPS-002. SQL001–027, member endpoints and frontend are deployed to production. Remote rollback resolution/financial/matching tests and authenticated mobile/authorization smoke passed; operational events/consents remain unpublished. Auth/CORS/EXECUTE-only rules remain in member-api.md.

POST /member/matching/resolve accepts an exact JSON object: applicationId UUID, requestKey UUID, action transfer/store/refund/cancel. transfer requires only slotId string in addition; refund requires only outcome success/failure. Unknown fields/state/amount/actor are rejected. The server validates own account/application and returns {applicationId, action, newApplicationId: UUID|null}. Same key/input returns the stored result; changed input conflicts409. Invalid input422, other owner403, closed/stale/financial/consent/period conflicts409. No public worker endpoint.

Transfer cancels the source with TRANSFERRED and creates a linked WAITING/PAID application with the same successful original-payment reference or membership. No payment attempt is copied. Only failed/stored choices can transfer; open published target before its match time, current required consent, membership period and overlapping/duplicate participation are checked again. A partial unique index permits one submitted PAID application per original payment. Store excludes the source from matching without freezing membership period. A failed refund excludes matching and preserves original-transaction retry; successful full refunds are unique per original payment. Used membership partial/full refunds remain restricted by PAY-008/RES-001.

Cancel before event start sets CANCELED_EARLY or CANCELED_LATE using the server cutoff. Late credit is not restored/refundable. Early refund requires a separate explicit command. Remaining valid4–6 participants retain their table with TABLE_UPDATED outbox; invalid/three-person groups are invalidated and queued for matching inside their selected scope. All resolution commands acquire matching-state then actor advisory locks and application/payment/membership rows; request result/audit/table/queue/outbox changes are atomic. Actual room/venue/notification delivery is still pending.

GET /member/matching adds applicationStatus/paymentStatus/attendanceStatus/stored/resolutionReason, canResolve/canCancel/canRefund, refundCutoffAt and safe open alternatives. These are UI capabilities; POST always revalidates. No payment/peer identity/profile/relationship records are serialized. /member/intake/refund delegates to the same server resolution state machine for compatibility.
